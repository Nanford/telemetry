# 阶段2 现场清单：SLAM 标定 + 狗端 point_id 改造

> 目标：让"0 匹配"变成真实读数。前置（阶段1）已完成——config.js 里 23 垛的**真实 CAD 相对坐标**已上线。
> 本阶段只做一件事：**把每次开机漂移的 Go2 SLAM 系，锁到这套 CAD 系上**。

---

## 0. 先纠正一个直觉（很重要）

你设想的"**到每个垛位、看上报数据、再改代码**"——方向对，但两处要修正：

1. **不用采 23 个点，只需 2~3 个锚点。** 23 垛的相对形状 CAD 已经给全了（间距/朝向/尺寸都是实测），
   现场缺的**只是把这个形状整体旋转+平移对齐到 SLAM 系**——这是一个刚体变换，3 个未知数
   (旋转 θ、平移 tx、ty)，2 个分得开的锚点就能解，3 个更稳。采 23 个纯属浪费且更容易错。

2. **不用手改坐标，跑脚本自动算。** 你现场只负责"把狗精确摆到已知点、读它报的 SLAM x/y"，
   把 2~3 组读数喂给标定脚本，脚本算出 (θ, tx, ty) 一把写回。手改 23 个坐标既慢又会引入误差。

**所以现场循环 ≈ 采 2~3 锚点 → 跑一条命令 → 重启 → 验证，约 15 分钟。** 代码我提前写好。

## 1. 架构决策（为什么 config.js 坐标不动）

- **config.js 的 23 垛坐标保持 CAD 系不变**（前端地图靠它画成正的矩形；若改成 SLAM 系，房间会
  被旋转到画布边界外、被 withinBounds 裁掉——阶段1 踩过的同一个坑）。
- 标定产出的**只是一个变换 `{theta, tx, ty}`**，存进服务器本地 `backend/src/calibration.json`（后端启动读入 `config.slam.calibration`；缺文件=恒等）。
- 后端在**匹配/渲染时**把进来的原始 SLAM 位姿 `pos_x/pos_y` 先过这个变换 → 落到 CAD 系 → 再匹配 config 的垛位、再画轨迹。
- **数据库只存原始 SLAM 位姿**（不动）。⇒ **改了 transform，历史批次自动追溯重匹配、永远不用重走。**

一句话：**垛位坐标是死的（CAD），变换是活的（每次开机可能要重标），两者解耦。**

## 3. 现场快速循环

### 前置 — 部署本阶段代码（进库房前、联网时做一次）
标定支持的后端代码要先上线（默认恒等变换，不改任何现有显示，部署 100% 安全）。
> 需要 Claude 先把阶段2代码 commit+push 到 GitHub（约 30 秒）；然后在服务器上：
```bash
cd /opt/telemetry
git pull --ff-only                      # 应看到新提交
sudo systemctl restart telemetry-api    # 后端加载标定支持(此时无 calibration.json = 恒等)
# 前端本阶段无改动，可不重构；如同时带阶段1未部署改动则照 DEPLOYMENT_GUIDE §3.1 重构前端
curl -s http://127.0.0.1:8011/api/v1/health   # 期望 200
```
判据：health 200、后端日志无报错。此时行为与部署前完全一致（未标定态）。

### Step 0 — 狗端切"只报原始位姿"（一次性，5 分钟）
让后端当唯一匹配裁判，狗别自己盖 point_id（否则会用没标定的示意坐标盖出错标签、毒化后端）。
```bash
# 在 Pi 上：把 POINTS_FILE 指向空点表（不改代码，纯配置）
cat > /opt/go2-env-agent/app/config/points.empty.yaml <<'EOF'
area_id: A-1-2
points: []
EOF
# 编辑 settings.env: POINTS_FILE=/opt/go2-env-agent/app/config/points.empty.yaml
sudo systemctl restart go2-env-agent
```
判据：`mosquitto_sub` 看到上报里 `"point_id": null`（`pose.x/y` 照常有值）。

### Step 1 — 采 2~3 个锚点（核心，10 分钟）
锚点 = **精确 CAD 坐标已知、且实物好定位**的点（推荐结构柱底、南门中线、走道两端）。
把狗**精确摆到锚点上**（狗身中心对准地面标志），读它当前报的 SLAM x/y：
```bash
# 现场看狗实时 x/y（原始 SLAM 系，地图此时看不到它，用 MQTT 直读）
mosquitto_sub -h <broker> -u <user> -P <pass> -t 'devices/Go2/telemetry' -v \
  | grep -o '"x":[0-9.-]*,"y":[0-9.-]*'
```
每个锚点记一行：`CAD坐标(cx,cy)  ↔  SLAM读数(sx,sy)`。**锚点尽量分得开**（如西头一个、东头一个），
基线越长、θ 越准（50m 基线、摆位误差 0.2m → θ 误差约 0.2°，够用）。

### Step 2 — 解变换（1 分钟）
把每个锚点的 `CAD坐标:SLAM读数` 传给脚本（`<sx>,<sy>` 换成 Step1 读到的真实值）：
```bash
python tools/solve_calibration.py \
  --anchor 30.5,0:<sx1>,<sy1> \
  --anchor 2.21,20.05:<sx2>,<sy2> \
  --anchor 52.52,20.05:<sx3>,<sy3> \
  --out /opt/telemetry/backend/src/calibration.json
# 输出 theta/tx/ty + 残差 rms（rms < 0.3m 才算好），并把结果写进 calibration.json
```

### Step 3 — 重启后端（30 秒）
`calibration.json` 是**服务器本地文件**（已 gitignore，`git pull` 不会动它），后端启动时读入。
```bash
sudo systemctl restart telemetry-api
# 确认已加载: 起来后看日志无报错即可(缺文件=恒等, 有文件=生效)
```
> 若在 Pi/笔记本上算的，把生成的 `calibration.json` scp 到服务器 `backend/src/` 再重启。

### Step 4 — 验证（3 分钟）
1. **追溯重匹配**：打开"巡检批次"里**今天已经录的那一批**，看点位是否开始命中、读数上墙——
   不用重走就能验证坐标对不对。
2. **走一圈**：遥控单程（上排东→西、下排西→东，每垛停 ≥15s），看巡检地图上点位实时点亮。
验收：命中率 > 90%、轨迹与垛位对齐、热力图切回按垛位显示。

## 5. 出问题怎么办

| 现象 | 原因 | 处理 |
|------|------|------|
| 解出的 rms 残差 > 0.5m | 锚点摆位不准 / 锚点太近 | 重采，锚点选更分得开的、实物更明确的 |
| 走一圈只命中一半 | 中途 SLAM 丢定位(fix=0) | 看 fix 比例；丢定位段本就不匹配，非标定错 |
| 关机重开后又不准了 | SLAM 每次开机原点/朝向变 | 每次开机重跑一遍 Step1~3；长期兜底=地面固定锚点每次开机自动重定位（阶段3再说） |
| 温湿度大面积缺失 | DHT 间歇失灵（与定位无关） | 独立问题，考虑重试/换传感器 |
